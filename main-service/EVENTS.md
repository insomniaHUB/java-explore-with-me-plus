# События: общая модель и интеграция

Ветка `main_svc_events`, основа — `main_svc` после пользователей и категорий.

## Границы

Реализованы POST/GET `/users/{userId}/events`, GET/PATCH
`/users/{userId}/events/{eventId}`, GET `/admin/events`, PATCH `/admin/events/{eventId}`.
Публичные события, подборки и обработка заявок остаются отдельными задачами команды.

Общие классы находятся в `ru.practicum.ewm.events`:
- `model.Event`, `EventState`, `Location` (координаты в таблице events);
- `dto.EventFullDto`, `EventShortDto`, `LocationDto`, входные DTO;
- `repository.EventRepository`, `mapper.EventMapper`.

Связи используют существующие `users.model.User` и `categories.model.Category`.
DTO используют общие `UserShortDto` и `CategoryDto`.
Mapper не обращается к БД или статистике: счётчики передаются аргументами.
Строки JSON дат имеют вид `2026-10-07 12:00:00`; `uuuu` во входных DTO
позволяет Jackson строго отклонять несуществующие календарные даты.

## Поставщики счётчиков — обязательная интеграция соседних частей

Нужно добавить по одному Spring bean, реализующему:

1. `events.metrics.ConfirmedRequestsProvider#countConfirmedRequests(Set<Long> eventIds)`.
   Владелец — часть заявок. Результат `Map<Long, Long>`, только статус CONFIRMED,
   пакетный GROUP BY по событиям. Поле-счётчик в Event отсутствует.
2. `events.metrics.EventViewsProvider#countUniqueViews(Set<Long> eventIds)`.
   Владелец — публичные события/статистика. Результат `Map<Long, Long>`.
   Уникальные IP (`unique=true`) по URI `/events/{id}` и согласованному имени приложения.
   `/events` не прибавляется к просмотрам каждого события. Нужен пакетный запрос.

Сигнатуры предложены для согласования с Викторией и Сергеем; реализации в этой ветке
не добавляются, чтобы не дублировать их задачи. Нет production-заглушек с нулевыми ответами.

Отсутствующий ключ в УСПЕШНО полученной Map означает ноль.
При сбое нельзя возвращать пустую Map: поставщик должен бросить
`ServiceUnavailableException` (HTTP-сбои RestClientException также преобразуются в 503).
Map=null, null-ключи/значения и отрицательные значения обрабатываются как 503;
корректное значение счётчика 0 допустимо.

До подключения обоих поставщиков приложение запускается, создание события работает
(реальные начальные значения равны нулю), пустые списки возвращаются без обращений.
Чтение непустых результатов и PATCH существующего доступного события возвращают 503.
Это явная незавершённая командная интеграция, а не готовность всей системы к автотестам.

## Транзакции и лимит

Изменение события использует `EventRepository.findByIdForUpdate` с PESSIMISTIC_WRITE.
Часть подтверждения заявок должна брать ту же блокировку Event В СВОЕЙ транзакции,
до подсчёта CONFIRMED, проверки лимита и обновления заявок. Использовать основной
datasource, не кеш и не реплику; рекомендуемый уровень изоляции — PostgreSQL READ COMMITTED.
Односторонняя блокировка в событиях не защищает от кода заявок, игнорирующего этот протокол.

Новый ненулевой лимит ниже текущего числа CONFIRMED возвращает 409. Лимит 0 — без ограничений.
Это предложенное командное правило, требующее подтверждения с владельцем заявок.
Изменение requestModeration не меняет автоматически статусы существующих заявок.

Поставщики вызываются до изменения Entity. При недоступности счётчиков PATCH
не сохраняет изменения. Запись/модерация выполняются в транзакции сервиса.
При публикации проверяется PENDING и дата не ранее чем через час от публикации.
При изменении даты уже опубликованного события используется исходный publishedOn.
Пользовательские даты проверяются относительно текущего времени + 2 часа.
Clock вынесен в bean `eventClock` для воспроизводимых тестов границ времени.

## Общие точки изменения

- В `schema.sql` добавлены events, внешние ключи и индексы. Пользователи и категории не дублируются.
- В CategoryService закрыт TODO: используемую категорию удалять нельзя (409); FK защищает и от гонки.
- В ErrorHandler нейтральная причина ConflictException, 400 для неверного JSON и параметров,
  503 для недоступных счётчиков. Исправление также позволяет size=0 у пользователей/категорий
  возвращать 400 вместо попадания в общий обработчик 500.
- Пагинация событий использует точные setFirstResult(from)/setMaxResults(size), сортировка по id.
  Существующая округляющая пагинация пользователей/категорий не изменялась.
- EventQueryRepository загружает category/initiator вместе с событиями: без N+1 и без лишнего COUNT.

## Проверки

Из корня проекта: `mvn -pl main-service -am -Pcheck verify`.
HTTP/сервисные тесты используют явные mock-поставщики счётчиков только в тестовом контексте.

Для PostgreSQL-проверок нужна отдельная БД: перед каждым тестом очищаются events/categories/users.
Тест проверяет, что имя БД заканчивается на `_test`. Не указывать рабочую БД.

Первый запуск тестового контейнера:

```powershell
docker run --name ewm-events-test-db --memory 256m --cpus 1 -e POSTGRES_USER=dbuser -e POSTGRES_PASSWORD=12345 -e POSTGRES_DB=events_test -p 127.0.0.1:55434:5432 -d postgres:16.1
docker exec ewm-events-test-db pg_isready -U dbuser -d events_test
```

Если контейнер уже создан: `docker start ewm-events-test-db`.
После сообщения accepting connections:

```powershell
mvn -pl main-service -am -Pcheck verify "-Devents.db.tests=true"
docker stop ewm-events-test-db
```

При необходимости переопределяются EVENTS_TEST_DB_URL, EVENTS_TEST_DB_USER, EVENTS_TEST_DB_PASSWORD.
По умолчанию: jdbc:postgresql://localhost:55434/events_test, пользователь dbuser, пароль 12345.

Проверки включают реальные COMMIT (нет общей откатываемой транзакции теста):
- создание через API и связи с пользователями/категориями;
- цикл отмена -> повторная модерация -> публикация, запрещённые переходы;
- PATCH с null/false/0;
- фильтры и некратное смещение from=1,size=2;
- отсутствие N+1 и пакетные вызовы обоих поставщиков;
- отсутствие изменений в БД после ответа 503;
- лимит, защита используемой категории и HTTP 400 для size=0;
- блокировка Event между двумя независимыми транзакциями PostgreSQL.

В тесте блокировки ожидается сообщение PostgreSQL `canceling statement due to lock timeout`;
это проверяемый сценарий, а не падение набора тестов.

Результат локальной проверки: 67 тестов основного сервиса без ошибок и пропусков
(27 HTTP, 24 сервисных, 5 контрактов счётчиков, 11 PostgreSQL).
Checkstyle и SpotBugs прошли.
